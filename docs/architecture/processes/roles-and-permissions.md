# Роли, права и зоны ответственности

**Сводка планов по кабинетам** — [`../cabinets.md`](../cabinets.md) (префиксы `/a`, `/o`, `/s`, `/b` и защита `RequireCabinet`).

**Реализация в веб** — `apps/web/src/auth/role-panels.ts` и маршруты в `App.tsx`. **Справочники «склад» / «товар и калибр» (создание и удаление):** в UI — раздел `/a/settings/catalog` (вкладка «Товары и калибры», роли `admin` и `manager`); на API — `inventoryCatalogWrite` в `apps/api/src/http/route-auth.ts`. Код калибра уникален **внутри товара** (`product_group` + `code`), не глобально. **Закуп и кладовщик** выбирают склад/калибр в накладной, но **не** создают/удаляют эти сущности через `POST/DELETE` при включённой авторизации. **Оптовики:** `POST /wholesalers` — `admin` / `manager` / `seller` (`wholesalerCreate`); снятие — только руководство (`inventoryCatalogWrite`). В кабинете продавца (`/s`) — кнопка «Добавить» в выборе оптовика при оптовой продаже.

Ориентир ассистента: [`AGENTS.md`](../../../AGENTS.md).

## Принцип доступа

Права выдаются по 4 измерениям:

1. `Роль`
2. `Подразделение или склад`
3. `Тип документа`
4. `Действие` — просмотр, создание, подтверждение, проведение, отмена, экспорт

## Основные роли

### Админ
Полный доступ к настройкам, справочникам, пользователям, ролям и аудиту.

### Руководитель
Как админ по экранам: кабинет `/a`, те же панели (включая склады/калибры и сотрудников), доступ ко всем кабинетам. На API — те же бизнес-права, что у руководства в `route-auth.ts`. Ограничение: при управлении учётками **не** выдаёт роли `admin`/`manager` и **не** меняет чужие учётки с этими ролями (см. `register-admin-user-routes.ts`).

### Закупщик
Создает закупочные накладные, прикладывает фото документов, видит свои закупки и связанные поступления.

В MVP **отдельной панели «закупщик» нет:** сценарии закупки и поступления на склад — в одном контуре с **кладовщиком**; целевой план **отдельных кабинетов** — [`../cabinets.md`](../cabinets.md). Колонка «Закупщик» в матрице ниже — для будущего разделения.

### Кладовщик
Подтверждает поступления, распределяет товар, формирует отгрузки в рейс, проводит инвентаризацию склада.

### Логист
Создает и ведет рейсы, назначает машину и водителя, контролирует статусы отгрузки и приемки.

### Приемщик
Подтверждает приемку рейса, фиксирует расхождения, прикладывает фото повреждений.

### Продавец
Принимает свой товар, видит остатки, оформляет продажи, долги, оплаты долгов и списания в пределах своих прав.

### Бухгалтер
Контролирует оплаты, дебиторку, расходы, сверки и финансовые отчеты.

## Ограничения по контексту

### Склады
- закупщик видит только связанные с ним закупки
- кладовщик работает только со своим складом
- руководитель и админ видят все склады

### Рейсы
- продавец видит только рейсы, где он назначен приемщиком или продавцом
- приемщик видит только активные рейсы своей зоны
- логист видит все рейсы в своей ответственности

### Продажи и долги
- продавец видит только свои продажи и долги
- бухгалтер видит все продажи и все оплаты
- **Оплаты долга клиента** (`POST /api/accounting/receivables/:saleId/payments`) — **`admin` / `manager` / `accountant` / `seller`** (`receivablePaymentWrite`). Полевой продавец — только по закреплённым рейсам (кнопка в отчёте `/s/reports` и `/a/reports`). **Оплаты тепличнику** (`POST /api/accounting/payables/:documentId/payments`) — только **`admin` / `manager` / `accountant`** (`accountingWrite`).
- Расходы по рейсу (`/api/accounting/trips/:tripId/expenses`) — те же роли `accountingWrite`.
- Расходы закупщиков (`/api/accounting/purchaser-expenses`) — зарплата и прочее; чтение `accountingRead`, запись `accountingWrite`.

**Ограничение по складу (scoped роли):** у пользователя с ролями `warehouse` или `receiver` и `scope_type = warehouse`, `scope_id = <id склада>` списки **`GET /api/batches`** и **`GET /api/purchase-documents`** содержат только строки этого склада; чужой документ на **`GET /api/purchase-documents/:id`** — ответ **403**. См. `apps/api/src/auth/warehouse-scope.ts`.

**Закупщик и накладные:** при создании накладной в PostgreSQL сохраняется **`created_by_user_id`** (JWT `sub`) и при выборе в форме — **`purchaser_user_id`**. Учётная запись с глобальной ролью **`purchaser`** (без `admin`/`manager`) в списке и карточке накладной видит только документы **без закупщика** (наследие) или **со своим** эффективным закупщиком (`purchaser_user_id`, иначе `created_by_user_id`). См. `apps/api/src/auth/purchase-scope.ts`. **Правка строк** (`PUT /api/purchase-documents/:id/lines`) — роли **`admin`**, **`manager`**, **`purchaser`** (`purchaseDocumentLinesWrite`); у purchaser — только свои документы; только пока партии не в погрузочной и без движений (`linesEditable`).

**Рейс и полевой продавец:** у рейса есть **`assigned_seller_user_id`** (кто закреплён «в поле»). Для **`GET /api/trips`** и доступа к **`GET /api/trips/:id`** / отчёту учётная запись с **только** полевой ролью `seller` видит только рейсы, закреплённые именно за ней; неназначенные и чужие рейсы скрыты/дают **403**. Назначение выполняется отдельным действием **`POST /api/trips/:tripId/assign-seller`** (“Отгрузить с рейса”) с ролями `admin`, `manager`, `logistics`. **Догрузка** в погрузочную накладную (в т.ч. с другого склада) **разрешена в любое время**, в том числе после закрепления продавца — кнопка «Догрузить товар» в карточке ПН. См. `assert-trip-warehouse-loading.ts`.

**Реализация в API (MVP, текущий код):** в таблицу `trip_batch_sales` пишется `recorded_by_user_id` (пользователь из JWT при `POST /batches/…/sell-from-trip` и `POST /sync` с `sell_from_trip`). Для учётной записи с **глобальной** ролью **только** `seller` (без `warehouse`, `logistics`, `manager` и т.д., см. `isGlobalSellerOnly` / `isFieldSellerOnly`) блоки **`sales`** и связанные **`financials`** в **`GET /api/trips/:tripId/shipment-report`** строятся только по таким строкам; **отгрузка в рейс** и **недостача** в отчёте — общие по рейсу. Дополнительно в том же ответе при этом фильтре отдаётся **`salesForTripStock`** — все продажи по рейсу в кг (для остатка «в машине» в форме продавца); остальные роли получают полный отчёт по продажам в одном блоке `sales`.

**Веб (кабинет `/s`):** учётная запись с **только** полевой ролью `seller` (`isFieldSellerOnly`) видит «Продажа» (`/s`), **«Отчёт по рейсу»** (`/s/reports`) и **«Траты / расчёт»** (`/s/expenses`) по закреплённым рейсам; пункт «Недостача по рейсу» (`/s/operations`) в боковом меню **не** показывается — недостача фиксируется на экране продажи. **Полевые траты** (`POST /api/seller-field-expenses`) — с кассы: грузчик / обед / палеты / аренда / материал / прочее; привязка к рейсу и дате; **к сдаче = нал − траты**. Бухгалтерские `trip_expenses` (топливо) продавец не ведёт.

**Веб (кабинет `/o`, закупщик):** роль **`purchaser`** без `admin`/`manager` (`isPurchaserScoped`) стартует со **сводки** `/o` (KPI и разрез по складам только по своим накладным). В сайдбаре — те же операционные разделы, что у админа: закупка, рейсы, погрузка (**создание ПН**), возврат на склад, догрузка, смена рейса. Создание/правка шапки рейса — как у логиста (`tripWrite`: admin/manager/logistics/**purchaser**). Закрытие, повторное открытие и удаление рейса — **только admin** (`tripCloseDelete`). **Расходы** `/o/expenses` — погрузка/обед/пенопласт/заправка/прочее на погрузочную накладную: видны в карточке ПН и входят в `expensesKopecks` отчёта по рейсу (вместе с `trip_expenses`); **не** увеличивают `extraCost` закупочной накладной и кредиторку тепличника; в периоде кассы `/b` тоже учтены. Без отчётов/продаж/недостачи/архива/настроек. Отчёт «Мои закупки» — со сводки («Подробнее») или `/o/purchase-by-purchaser`.

**Отчёт «закупки по закупщикам»:** **`GET /api/admin/purchase-by-purchaser?from=&to=`** (даты накладной `YYYY-MM-DD`) — роли **`admin`**, **`manager`**, **`purchaser`**. У purchaser без руководства ответ **только по своим** накладным (эффективный закупщик = JWT `sub`). Разрез закупщик × склад (сумма копеек строк + доп. расходы документа, кг, ящики), итоги по закупщику и по складу. UI: **`/a/purchase-by-purchaser`** (admin/manager); у purchaser зеркало **`/o/purchase-by-purchaser`**.

**Назначение продавца на рейс:** список кандидатов — **`GET /api/trips/field-seller-options`** (роли `admin`, `manager`, `logistics`), активные пользователи с глобальной ролью `seller`.

**Сводка KPI админа:** **`GET /api/admin/dashboard-summary`** — роли **`admin`**, **`manager`** (не для purchaser и прочих полевых).

**Погрузочная накладная и рейс (API):**
- **`POST /api/loading-manifests`**, **`…/add-batches`**, **`…/assign-trip`**, **`…/detach-trip`** — роли `admin`, `manager`, `warehouse`, `logistics`, **`purchaser`** (`ship` в `route-auth.ts`). У закупщика кнопка **«Готово — погрузочная накладная»** как у админа.

**Недостача по рейсу:** **`POST /api/batches/:batchId/record-trip-shortage`** — роли `admin`, `manager`, `warehouse`, `logistics`, `receiver`, **`seller`** (`SHORTAGE_ROLES` в `route-auth.ts`). У учётной записи с **только** полевой ролью `seller` (`isGlobalSellerOnly`) — только рейс, закреплённый за этим пользователем (иначе **403**), как у `sell-from-trip`.

- руководитель видит агрегаты и детализацию по ролям и регионам

## Разделение действий

### Создание
Пользователь может собрать черновик документа, но не проводить его без соответствующего права.

### Подтверждение
Подтверждение означает, что пользователь отвечает за корректность данных до проведения.

### Проведение
Проведение создает движения и должно быть доступно только ролям, которые реально управляют остатками и деньгами.

### Отмена
Отмена проведенного документа выполняется только через обратный документ или специальный административный сценарий с записью в аудит.

## Согласованное правило по оплатам долга

**Решение (заказчик):** погашение долга клиента принимает **продавец** (в отчёте по рейсу) и **админ / руководитель / бухгалтер**. Оплаты тепличнику — только бухгалтерия/руководство. См. также `../risks-and-guardrails.md` (риск 2).

## Критические запреты

- продавец не может вручную увеличивать свой остаток
- закупщик не может править чужие закупочные накладные и назначать продавца
- приемщик не может менять уже закрытый рейс
- бухгалтер не должен редактировать товарные количества в продажах
- документ с созданными движениями не должен редактироваться без следа в аудите
